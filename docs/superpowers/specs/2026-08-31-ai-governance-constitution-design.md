# StockSentinel AI 治理与项目宪法设计

Status: implemented

Date: 2026-08-31

## 背景

StockSentinel 已经采用“AI 主导执行、人负责方向与把关”的维护方式，但当前根目录
`AGENTS.md` 同时承担项目使命、产品原则、权限边界、开发流程、测试命令、编码规范和任务模板。
这种混合结构能工作，却有三个长期问题：

1. 每次 Agent 启动都会加载大量与当前任务无关的操作细节，挤占有效上下文。
2. 长期不变的产品价值与容易变化的命令、测试数量混在一起，难以判断冲突时谁优先。
3. 项目尚未把“小白优先、低注意力使用、用户体验优先”写成所有功能都必须遵守的最高原则。

本设计采用分层治理：项目宪法负责稳定价值和判断边界，`AGENTS.md` 负责自动加载入口与工作循环，
工程手册负责可变化的执行细节。

## 目标

- 让每个参与产品规划、实现和审查的 Agent 在开始工作前理解同一套产品原则。
- 允许用户只提出目标或痛点，由 AI 负责产品方案、范围、PRD、实现、验证和后续建议。
- 把小白用户、低注意力场景和用户体验变成硬性产品约束，而非可选优化。
- 建立数据真实性、量化有效性和诚实表达的最低标准。
- 减少入口文件噪声，同时保留现有安全边界、质量门和操作经验。
- 明确文档冲突、例外和宪法修订的处理方式。

## 非目标

- 不改变任何运行时代码、数据库、API、页面或告警语义。
- 不引入新的外部服务、依赖、自动化平台或多 Agent 编排系统。
- 不让 AI 永久脱离用户监督、自行决定投资目标、风险偏好或商业方向。
- 不在本轮清理全部历史 PRD 状态或解决现有产品待办。
- 不把所有专业知识塞进宪法；具体量化方法和工程做法继续按需读取。

## 决策：三层治理结构

### 1. `CONSTITUTION.md`：稳定的最高项目原则

宪法保持短小，只包含需要跨功能、跨技术方案长期成立的判断原则。目标篇幅为 80–160 行，
不记录测试数量、当前版本、具体库名或容易过期的命令。

宪法包含以下章节：

1. **使命与目标用户**
   - StockSentinel 是面向普通投资者的个人投研型量化决策支持平台。
   - 产品首先服务没有量化背景、没有大量时间盯盘的用户。
   - 产品不承诺预测市场，不替用户作出投资决定。
2. **小白优先**
   - 默认路径不得要求用户理解因子、指标、回测参数或市场术语。
   - 专业能力采用渐进式展开；高级功能不能破坏新手默认体验。
   - 每个重要结果优先解释“发生什么、为什么重要、可以做什么”。
3. **低注意力设计**
   - 系统主动监控、筛选、归纳和发现异常，用户无需持续盯盘。
   - 提醒少而重要，避免重复、无行动价值或制造焦虑的噪声。
   - 重要状态应可在短时间内理解，并支持用户稍后继续处理。
4. **用户体验优先**
   - 易理解、反馈、容错、可访问性和信任感属于功能完成标准。
   - 真实使用流程优先于参数数量和技术展示。
   - 当前即使只有项目所有者一名用户，也按可商业化的体验标准设计。
5. **真实数据与诚实表达**
   - 真实、可追溯的数据优先于表面完整；不得用演示或伪造数据冒充真实结果。
   - 显示数据来源、时间、新鲜度、覆盖不足和不确定性。
   - 数据不可用时明确降级或失败，不制造确定性结论。
6. **量化有效性**
   - 回测和选股必须主动防范未来函数、数据泄漏、幸存者偏差、过拟合和忽略交易成本。
   - 结果必须可复现、可解释，并与适当基准比较。
   - 漂亮收益率不能覆盖方法缺陷；风险和限制与收益同等重要。
7. **产品取舍**
   - 能立刻解决真实决策问题，优先于功能数量和架构炫技。
   - 默认方案应简单、完整、可验证；复杂性必须由明确用户价值证明。
   - 新能力优先融入连续工作流，不堆积孤立页面或指标。
8. **人与 AI 的权责**
   - 用户负责目标、真实反馈、风险边界、商业方向和最终否决权。
   - AI 负责主动提出专业方案、确定默认范围、产出 PRD、执行、验证和沉淀经验。
   - 涉及不可逆数据、凭据、付费服务、架构替换或真实资金行动时必须升级给用户。
9. **完成与学习**
   - “完成”以可验证的用户结果为准，不以生成代码或文字报告为准。
   - 失败、取舍和新知识应沉淀到版本化文档、测试或工具中。
10. **冲突、例外与修订**
    - Agent 发现具体需求与宪法冲突时必须指出，不得静默绕过。
    - 用户的明确指令具有最终项目决策权；若形成长期变化，应同步修订宪法。
    - 宪法是活文档，但修订必须明确说明原因和被改变的原则。

### 2. `AGENTS.md`：自动加载的入口与执行契约

`AGENTS.md` 目标控制在 100–180 行。它不重复宪法全文，而是在开头强制要求：

- 所有规划、实现、审查 Agent 在采取项目行动前完整阅读 `CONSTITUTION.md`。
- 新会话只需读取一次；宪法发生变化、切换项目或启动独立子 Agent 时重新读取。
- 无法读取宪法时，不得作出产品或实现决策。

其余内容仅保留：

- 项目身份和运行模式。
- 指令优先级与冲突处理。
- 每次会话的开工检查。
- PRD → issue → 实现 → 验证 → 提交 → 记录的工作循环。
- 必须升级给用户的事项。
- 收工检查与固定汇报格式。
- 指向 `CONTEXT.md`、`CLAUDE.md`、工程手册、领域文档、路线图和 ADR 的导航。

### 3. `docs/agents/engineering-playbook.md`：可变化的工程手册

从现有 `AGENTS.md` 迁移以下细节，不改变其语义：

- 后端、前端和数据抓取的测试命令。
- 量化引擎编码风格和测试规范。
- Git、worktree、commit 和构建产物约定。
- 新指标、新数据源和 bug 修复模板。
- 故障排查、长会话交接和首次接手清单。

工程手册由 `AGENTS.md` 按任务类型要求读取：修改代码、制定实施计划或代码审查时必须读取；
纯产品讨论和只读状态查询不需要全文加载。

## 指令优先级

平台安全和工具权限不属于仓库文档，始终优先。项目内部按以下次序解释：

1. 用户当前的明确指令；如与宪法冲突，Agent 先指出冲突，再按用户最终决定执行。
2. `CONSTITUTION.md` 的长期产品与治理原则。
3. 根目录及任务目录适用的 `AGENTS.md` 操作规则。
4. 已批准的 PRD、issue、执行计划和 ADR。
5. `CONTEXT.md`、`CLAUDE.md`、领域文档和工程手册中的事实与惯例。
6. 既有代码模式；代码与文档冲突时应调查，而不是默认代码永远正确。

短期例外不得自动变成长期原则。若用户的决定将持续影响后续功能，Agent 应提出宪法或 ADR 修订。

## Agent 启动与工作流

```text
新 Agent / 新会话
  → Codex 或其他工具自动加载 AGENTS.md
  → AGENTS.md 强制读取 CONSTITUTION.md
  → 读取 CONTEXT.md 与当前任务所需的最小文档
  → 检查仓库和未提交工作
  → 形成方案或执行计划
  → 实现并验证真实结果
  → 独立审查高风险或复杂改动
  → 更新 PRD / issue / ADR / CHANGELOG
  → 汇报结果、限制与下一步
```

对子 Agent 或独立审查 Agent，主 Agent 的任务说明必须提醒其遵守根目录指令；独立执行上下文也应自行加载
`AGENTS.md` 和宪法。测试命令本身不需要重复加载产品文档，但解释测试结果和作出取舍的 Agent 需要。

## 文件变更范围

正式实施阶段只修改或新增以下治理文件：

- 新增 `CONSTITUTION.md`。
- 重写根目录 `AGENTS.md`，保留入口、工作循环、安全边界和文档地图。
- 新增 `docs/agents/engineering-playbook.md`，承接现有详细工程规范。
- 更新 `CONTEXT.md` 的文档地图和接手顺序。
- 更新 `CHANGELOG.md`，记录治理结构、验证结果和未决事项。

不修改 `.scratch/stock-logos/`、前后端源代码、静态构建产物或真实数据库。

## 冲突和失败处理

- **宪法缺失或链接失效**：停止产品设计和代码实现，先修复治理入口。
- **宪法与 AGENTS 冲突**：遵守宪法并修正文档冲突；不得让两套规则长期并存。
- **工程手册与实际命令不符**：以可验证的仓库配置为依据，更新手册并记录原因。
- **用户需求与宪法冲突**：明确指出影响和推荐方案，由用户决定一次性例外或正式修宪。
- **规则无法机械验证**：在交付报告中披露，必要时转化为测试、lint 或审查清单。
- **文档过长或重复**：保留单一事实来源，以链接代替复制。

## 验证与验收

设计实施后执行以下验证：

1. 确认 `AGENTS.md` 开头明确要求完整读取 `CONSTITUTION.md`。
2. 检查所有新增和修改的相对链接均指向存在的文件。
3. 检查宪法不包含版本号、固定测试数量或容易过期的实现细节。
4. 检查现有 `AGENTS.md` 中的安全边界、质量门和操作经验均在新入口或工程手册中有归属。
5. 搜索重复或矛盾的强制规则，确保每项原则只有一个权威来源。
6. 运行文档格式和空占位检查，禁止遗留 `TBD`、未解释的 `TODO` 或断链。
7. 运行仓库既定的后端测试、数据抓取冒烟、前端 lint 和 build，确认纯文档改造未污染代码基线。
8. 在全新 Agent 会话中验证其能够复述：目标用户、三项核心产品原则、量化真实性要求、升级边界和工作循环。

验收标准：新 Agent 无需读取一份巨型手册，就能先获得稳定价值观，再按当前任务加载必要操作细节；
现有开发纪律不得因拆分而丢失。

## 风险与缓解

- **规则被拆散后难找**：`AGENTS.md` 提供按任务类型组织的文档地图。
- **宪法变成口号**：PRD 验收、代码审查和真实流程验证必须引用相关原则。
- **重复规则产生漂移**：宪法只写原则，工程手册只写执行方法，不复制相同段落。
- **Agent 跳过宪法**：在 `AGENTS.md` 第一节设置硬性读取门槛，并用新会话验证。
- **治理文件继续膨胀**：新增细节优先进入按需文档或 Skill，不继续堆入入口文件。
- **完全自治造成方向漂移**：AI 可以闭环执行，但产品方向仍通过用户反馈和重大决策升级校准。

## 后续演进边界

本轮只建立清晰、可靠的文档治理。以下能力在观察实际使用后另行立项，不随本设计一起实现：

- 自动检查文档链接、重复规则和陈旧测试数量的 lint。
- 产品规划 Agent、实现 Agent、量化审查 Agent 和体验评估 Agent 的固定多 Agent 工作流。
- 基于真实用户任务的产品 Eval 套件。
- 定期整理过期 PRD、issue 和技术债的后台任务。
- 将稳定工作流封装为项目专用 Skills。
